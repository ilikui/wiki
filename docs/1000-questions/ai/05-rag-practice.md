**专栏⑯·第5篇：RAG 实战——分块、向量、检索、对齐，把笔记变成可检索的知识库**

📎 第4篇：LLM 架构基础 → <https://v.flomoapp.com/mine/?memo_id=MjUwNTg2Mjk3>

第3篇讲了 Embedding 和 RAG 的坑。这篇给一套能落地的 RAG 实战流程——把你的 flomo 笔记（或任何知识库）变成一个"问它就能答"的系统。

**一、RAG 全链路——五个环节，每个都可能翻车**

用户提问 → ① 问题向量化 → ② 向量检索 Top-K → ③ 拼 prompt → ④ LLM 生成 → ⑤ 回答

**翻车点分布**：① 问题太长/太短语义偏移；② 检索到"相关但不回答"的内容；③ prompt 没约束"只准用检索内容"；④ LLM 编造（幻觉）；⑤ 回答没引用来源。

**二、分块策略——最影响检索质量的一步**

**三种分块方式的取舍：**

- **固定长度分块**（256/512 tokens）：实现最简单，但会把句子拦腰切断（第3篇坑1A）

- **段落/语义分块**（按标题、按空行、按句子边界）：保语义完整，是推荐做法

- **层级分块**（文档→章节→段落三级索引）：检索到段落，返回给 LLM 时带上章节标题——上下文最全


**overlap 怎么设：** 相邻块重叠 100-150 tokens（至少一个完整句子），防止边界上下文丢失（第3篇坑1B）。

**你的笔记场景**：flomo 卡片本身已经是"语义单元"——按卡片分块比按 token 分块更合适。但专栏长文（1000 问那种 9000+ 字）需要再切——按 ▎ 标题切，每块保留标题作上下文。

**三、向量维度与检索——别过度设计**

- 1000 条笔记：384 维（bge-small / text-embedding-3-small）够用

- 10 万条：1536 维（text-embedding-3-large）或混合检索

- **混合检索**（BM25 关键词 + 向量语义）比纯向量好——专有名词（AUTOSAR、BswM、CRC）向量可能跑偏，关键词能兜底


**四、prompt 约束——"只准用检索内容"必须写死**

你是我的知识库助手。只基于下面提供的资料回答。如果资料里没有答案，直接说"我的笔记里没有相关内容"，不要猜测或使用训练知识。

**为什么必须加：** 不加这个约束，LLM 一定会用训练知识编一个"听起来对"的答案——比说"不知道"危险得多（第3篇最隐蔽的坑）。

**五、评估——RAG 系统好不好，测四个指标**

1. **检索召回率**：该检索到的文档，检到了多少（人工标注 20-50 个问题对）

2. **回答准确率**：回答内容跟检索内容一致吗（有没有幻觉）

3. **引用正确率**：引用的来源真能支撑回答吗

4. **失败模式**：收集"答错了"的案例，反推是分块问题还是检索问题还是 prompt 问题


**六、Karpathy 的 LLM Wiki 思路——比 RAG 更进一步**

你记过的 LLM Wiki（<https://github.com/nashsu/llm_wiki>，Karpathy 方法论）：不是每次从零检索，而是 **用 LLM 持续构建结构化 Wiki**——每次问答后把新知识沉淀成条目，下次直接查 Wiki。跟 RAG 的区别：RAG 是"每次现查"，LLM Wiki 是"越用越厚"。对应你的知识管理6层闭环：RAG 管检索，LLM Wiki 管积累。
