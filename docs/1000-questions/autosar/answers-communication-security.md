## 通信栈 Q1：CAN 通信从 PDU 发到总线，COM→PduR→CanIf→Can 每层做什么？

> 来源：[Flomo 原笔记](https://v.flomoapp.com/mine/?memo_id=MjUyNDgyNDA1) · 952 字

**发送路径（Tx）**

- **COM**：把应用信号打包成 PDU，按配置的周期/事件发送，并处理信号级配置。
- **PduR**：根据路由配置将 PDU 转发到目标接口，不负责信号解释。
- **CanIf**：管理 PDU 与 CAN 帧的映射，包括 CAN ID、DLC、帧格式和硬件对象等，并处理发送确认。
- **Can 驱动**：面向 CAN 控制器，完成收发、寄存器操作、中断与 Bus-Off 相关处理。

**接收路径**大致反向：Can 收帧 → CanIf 匹配 → PduR 路由 → COM 解包成信号 → RTE 提供给 SW-C。

**排错原则**：COM 查信号与 I-PDU 配置；PduR 查路由表；CanIf 查 CAN ID、HRH/HTH 与映射；Can 驱动查控制器状态、错误计数和中断。具体调用链以项目生成代码为准。

## 通信栈 Q2：多个节点接收同一 CAN 报文，AUTOSAR 如何处理？

> 来源：[Flomo 原笔记](https://v.flomoapp.com/mine/?memo_id=MjUyNDgyNDA4) · 1004 字

同一 CAN 报文被多个 ECU 接收是正常的广播通信，不等同于冲突。接收节点由 CanIf 根据 CAN ID 等配置匹配接收 PDU；PduR 可按配置将一个接收 PDU 路由给多个目的；COM 将 PDU 解包为信号，再通过 RTE 供相关 SW-C 使用。

需要真正防范的是配置歧义和不一致：

- 不同接收 PDU 错误地配置相同 CAN ID，可能导致匹配歧义。
- CAN ID、DLC、信号布局或字节序等配置与网络数据库不一致。
- 同一 ECU 内多个消费者需要同一信号时，应通过配置的路由与接口共享数据，而不是各自重复定义互相冲突的 PDU。

**总结**：一对多接收靠 CanIf 匹配、PduR 路由和 COM/RTE 数据分发；关键是保证配置一致性。

## 通信栈 Q4：为什么需要 PduR？COM 直接调用 CanIf 不行吗？

> 来源：[Flomo 原笔记](https://v.flomoapp.com/mine/?memo_id=MjUyNDgyNDY5) · 915 字

PduR（PDU Router）提供 PDU 级路由与解耦能力。若 COM 直接调用 CanIf，上层就会与特定总线接口绑定；Dcm、Nm 等其他模块也需要各自处理底层接口，增加总线扩展和维护成本。

PduR 的主要价值：

- **解耦**：上层模块提交 PDU，不必直接依赖 CAN、LIN 或以太网接口。
- **配置驱动路由**：路由关系由配置定义，减少把路径写死在业务代码里的情况。
- **一对多路由**：按配置将 PDU 分发给多个目标。
- **网关转发**：在支持的配置下，把接收 PDU 转发至另一总线/接口。

**总结**：PduR 是 PDU 级的路由中心；它减少模块之间的直接依赖，让路由和网关行为更容易配置与维护。

## SW-C 类型 Q5：Port Connector 怎么连？生成 RTE 前检查什么？

> 来源：[Flomo 原笔记](https://v.flomoapp.com/mine/?memo_id=MjYxMzU2Mjc5) · 1368 字

Port 是 SW-C 对外的接口端点；Connector 描述端口之间的连接关系。通常需要匹配提供端口（P-Port）与需求端口（R-Port）的接口类型，以及对应的数据元素或操作。

**典型工作流**：在 SW-C 设计工具中定义 Port / Interface → 导出并导入 ARXML → 完成 SW-C 到 ECU 的映射与连接配置 → Validate → Generate RTE。

**生成前检查清单**

- 每个必需的 R-Port 都有正确连接；可选端口需符合项目配置。
- P-Port / R-Port 方向和接口类型正确，S/R 与 C/S 语义相匹配。
- 数据元素类型、长度和接口定义一致。
- 跨 ECU 通信对应的 Signal、PDU、路由等配置完整。
- Runnable 的 Task 映射完整，SW-C 实例没有遗漏。
- ARXML 是最新版本，先运行 Validate 并处理报告，再生成代码。

一个接口名称相同不代表所有数据类型和语义都兼容；具体约束依 AUTOSAR 版本及配置工具校验规则而定。

## 功能安全 Q2：E2E 保护什么？如何检测 silent data corruption？

> 来源：[Flomo 原笔记](https://v.flomoapp.com/mine/?memo_id=MjUzNTQyMDI0) · 1079 字

E2E（End-to-End）保护的是发送方应用到接收方应用之间的数据完整性与时序/序列特征。CAN 帧 CRC 主要检测总线帧传输中的错误，无法单独覆盖 ECU 内部路由、缓存和数据拷贝等所有环节。

常见保护机制包括：

- **CRC**：检测数据损坏或非预期修改。
- **Counter**：检测重复、丢失或序列异常（具体检测能力依 Profile）。
- **Timeout / Data freshness**：监控数据是否在预期时间内更新。

检测到错误后，E2E 库通常提供状态给上层；它不自动决定应用必须采用哪种恢复策略。应用应根据安全分析和项目策略选择丢弃无效数据、短期保持上次有效值、使用安全默认值、上报 Dem 或进入降级/安全状态。连续错误不应无限期沿用旧值。

**总结**：E2E 检测端到端数据异常；错误后的应用行为由系统安全需求和具体实现决定。

## 信息安全 Q1：SecOC 如何防止 CAN 报文伪造与重放？

> 来源：[Flomo 原笔记](https://v.flomoapp.com/mine/?memo_id=MjUzNTQyMjc1) · 1046 字

SecOC（Secure Onboard Communication）通过认证信息与新鲜度机制保护配置启用的车载通信 PDU。

1. **消息认证码（MAC）**：发送方基于密钥和受保护数据（以及相关新鲜度信息）生成认证码；接收方验证认证码，阻止没有正确密钥的伪造报文及受保护数据被篡改。
2. **Freshness Value**：通过计数器或项目采用的新鲜度机制检测旧报文重放；接收方依据接收状态和新鲜度策略验证报文。
3. **密钥管理**：密钥生命周期、访问控制和安全存储需由项目的密钥管理方案保障；可结合 HSM/SHE 等平台能力，不能假定所有 ECU 都以同一方式存储密钥。

SecOC 会带来认证数据开销和计算成本，通常根据安全需求对选定 PDU 启用。具体 MAC 算法、截断长度、新鲜度同步方式及失败处理应遵循项目采用的 AUTOSAR 规范版本和安全配置。

**与 E2E 的区别**：E2E 主要检测随机故障和数据完整性/序列异常；SecOC 主要提供通信认证与防重放能力，两者目的不同，可按需求组合使用。

## 通信栈 Q3：Signal 和 PDU 的关系是什么？什么时候一个 PDU 放多个 Signal？

> 来源：[Flomo 原笔记](https://v.flomoapp.com/mine/?memo_id=MjUyNDgyNDYz) · 946 字

Signal 是应用层关注的数据项，例如车速、转速或开关状态；PDU 是通信栈中承载数据的协议数据单元。一个 PDU 可以按配置承载一个或多个 Signal，最终再映射到具体总线帧。

**适合合帧的情况**

- 多个信号来源相近、更新周期接近，且属于同一功能域。
- 合并后能更有效利用帧的数据区，降低总线开销。
- 信号布局、接收方和安全需求允许共享同一 PDU。

**不宜强行合帧的情况**

- 信号更新频率差异很大，导致低频信号被高频发送带着走。
- 某个信号的数据量较大，或有独立的时序、安全和接收要求。
- 信号布局变化会影响大量接收方，增加版本耦合。

**配置检查**：核对 Signal 的起始位、长度、字节序、符号属性与 PDU 长度；同时检查通信矩阵/ARXML 和生成代码是否一致。Classic CAN 与 CAN FD 的数据长度限制不同，具体以项目配置为准。

**总结**：Signal 是数据内容，PDU 是承载与路由单元；合帧需要权衡带宽利用率、更新周期、耦合程度和安全要求。
