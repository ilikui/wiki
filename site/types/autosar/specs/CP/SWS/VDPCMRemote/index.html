    This specification describes the functionality, the API and the configuration for the AUTOSAR Basic Software module VDP-CM Remote.].

    4. 定义 of terms¶

    原文标题：Definition of terms

    Terms: Description:
    Data point A data point refers to a data resource inside the vehicle with a well-defined semantic that can be collected (e.g. vehicle speed).
    Data point sample A data point sample refers to the value of a data point acquired at a specific point in time (e.g. vehicle speed at 12 am).
    DCA Remote A DCA Remote refers to a Data Class Adapter Remote. The Data Class Adapter Remotes are directly connected to a CM Remote and can directly access data points on the other side. They can be realized e.g. by integrator code, AUTOSAR Complex Device Drivers or a specific SWC.
    VDP Slot ID The VDP Slot ID refers to a dynamically associated ID to an abstract data point during the lifetime of a data collection task. The dynamic association is part of the protocol VDP and is established using the add dynamic configuration command.

    12. PduR¶

    In order to receive and transmit VDP messages on the communication bus, the VDP-CM Remote module interacts with the PDU Router .

    13. StbM¶

    In order to get a synchronized time value (Local Time Base derived from Global Time Base), the StbM module is used.

    14. NvM¶

    In order to load and store dynamic configurations, the NvM module can optionally be used.

    15. Det¶

    In order to be able to report development errors and to forward this information through DET to the communication bus, the VDP-CM Remote module interacts with the DET module . However, the interaction with DET is optional.

    19. Communication with PduR¶

    Communication configuration Upstream requirements: , ⌈ The VdpCmR shall use the content of VdpCmRCsl to configure its communication and security layer. ⌋

    Unsecure and secure PDU reception Upstream requirements: , ⌈ The VdpCmR shall receive PDUs that are transmitted unsecured (mandatory) as well as secured (optional, defined project specific). ⌋

    Rx PDU configuration Upstream requirements: , ⌈ The VdpCmR shall use the general purpose PDU defined by container VdpCmRCslRxPdu for reception from the PduR. ⌋

    In case of secured transmission are the PDUs already processed by SecOC and only the unsecured PDU part is passed from the PduR to VdpCmR. So the VdpCmR does not see any difference between secured and unsecured PDUs at reception.

    Unsecure and secure PDU transmission Upstream requirements: , ⌈ The VdpCmR shall be able to transmit PDUs unsecured (mandatory) as well as secured (optional, defined project specific). ⌋

    Unsecured Tx PDU configuration Upstream requirements: , ⌈ The VdpCmR shall use the general purpose PDU defined by the mandatory container VdpCmRCslTxPdu for transmitting unsecured PDUs using the PduR. ⌋

    20. Processing of VDP Messages¶

    The VdpCmR module receives VDP messages from the PduR via the Rx Data Path. These messages control VdpCmR as well as the connected DCA Remotes (realized as separate CDD in AUTOSAR).

    Incoming Messages Upstream requirements: , ⌈ The VdpCmR shall provide the functionality to receive VDP messages from one other ECU via the PduR module. ⌋

    Receive buffer Upstream requirements: , ⌈ The VdpCmR shall use a receive buffer of size VdpCmRRxBufferSize to store received VDP messages. ⌋

    Receive StartOfReception Upstream requirements: , ⌈ The VdpCmR shall return the receive buffer to the PduR when this calls VdpCmR_StartOfReception (see Figure ). ⌋

    Receive CopyRxData Upstream requirements: , ⌈ The VdpCmR shall copy the passed receive data into its receive buffer when the PduR calls VdpCmR_CopyRxData. ⌋

    Receive TpRxIndication Upstream requirements: , ⌈ The VdpCmR shall trigger processing the receive buffer in the next call to VdpCmR_MainFunction when the PduR calls VdpCmR_TpRxIndication. ⌋

    原文标题：DCA Configuration

    The VdpCmR interacts with the DCA Remotes, i.e. it configures them and collects the data provided by them.

    DCA Remote count Upstream requirements: ⌈ The VdpCmR shall communicate with the DCA Remotes configured inside container VdpCmRDcaRemotes. The number of the containers VdpCmRDcaRemote inside VdpCmRDcaRemotes define the number of DCA Remotes. ⌋

    DCA Remote names Upstream requirements: ⌈ The VdpCmR shall use the API of a DCA Remote to communicate with it as described in chapter . The prefix of the function names _functionXXX (like _AddDpDCfg) is configured through the name of the enclosing container VdpCmRDcaRemote, the shall be replaced by this. ⌋

    DCA Remote ID mapping Upstream requirements: ⌈ The VdpCmR shall realize a mapping between a DCA Remote ID and the corresponding DCA Remote by the configuration parameter VdpCmRDcaRemoteId that is contained inside the VdpCmRDcaRemote container. This allows calling the correct DCA Remote function when receiving a VDP message from the PduR containing just a DCA Remote ID. ⌋

    23. Remove dynamic 配置¶

    原文标题：Remove dynamic configuration

    Remove Dynamic Configuration Request Upstream requirements: , , , ⌈ The module VdpCmR shall verify the combinations of the flags (T_CYCLIC), (GLOBAL) and (DCA) together with the payload on validity and react on invalid combinations with an error according to the protocol specification. ⌋

    Remove Dynamic Configuration Request - cyclic Upstream requirements: , , ⌈ In case the (T_CYCLIC) flag is set, VdpCmR shall remove its internal cyclic transmission settings. ⌋

    Remove Dynamic Configuration Request - VDP Slot ID Upstream requirements: , , ⌈ In case no flag or the (T_CYCLIC) flag is set, VdpCmR shall iterate through the VDP_SLOT_IDs contained in the payload, find the corresponding DCA Remote and call _DeleteDpDCfg with the VDP_SLOT_ID. ⌋

    Remove Dynamic Configuration Request - Global Upstream requirements: , , ⌈ In case the (GLOBAL) flag is set, VdpCmR shall call _DeleteAllDpDCfgs for all existing DCAs. ⌋

    Remove Dynamic Configuration Request - DCA Upstream requirements: , , ⌈ In case the (DCA) flag is set, VdpCmR shall iterate through the DCAs contained inside the payload and call _DeleteAllDpDCfgs for each. ⌋

    24. Activation¶

    Activation state Upstream requirements: , , ⌈ The module VdpCmR shall activate the sampling in case the activation state (ACT) is set to 1 inside the activation request message or deactivate the sampling otherwise. ⌋

    Activation request payload Upstream requirements: , , , ⌈ The module VdpCmR shall decode all VDP_SLOT_IDs contained DDLE encoded inside the control message payload. ⌋

    Activation at remote DCA Upstream requirements: , , , ⌈ On reception of an activation request (CT = 2) with payload, the VdpCmR shall iterate through the provided VDP_SLOT_IDs and

    validate the VDP_SLOT_ID, and¶

    25. Trigger¶

    Trigger request - Transmission Upstream requirements: , , ⌈ On reception of a trigger request (CT = 3) with TX_TRIG = 1, the VdpCmR shall request sending the data message buffer in the next call to VdpCmR_MainFunction.

    If no payload is contained, the VdpCmR shall respond immediately with an acknowledge (ACK = 1) with no payload. ⌋

    The payload in trigger requests is optional. If contained the processing shall be done according to the following requirement.

    Trigger request - Sampling Upstream requirements: , , ⌈ On reception of a trigger request (CT = 3) with payload, the VdpCmR shall iterate through the provided VDP_SLOT_IDs and

    validate the VDP_SLOT_ID, and¶

    if successful, call the API _TriggerDpOneTimeSampling on the according DCA Remote with the VDP_SLOT_ID as parameter.¶

    ⌋

    In the previous requirement, it is not required that the sampling must occur immediately during the API call to _TriggerDpOneTimeSampling. It is allowed for the DCA Remote to sample later in e.g. the next main function cycle.

    26. Submission of 数据 Point Samples¶

    原文标题：Submission of Data Point Samples

    When a DCA Remote calls VdpCmR_AddSample, the VdpCmR stores the provided data suitably inside its data message buffer of configuration parameter size VdpCmRTxBufferSize. Beyond this, the function contains no further functionality unless the transmission is configured to be "on sample" for this specific data point.

    Adding data point samples Upstream requirements: , ⌈ The VdpCmR shall be able to receive data point samples with the service VdpCmR_AddSample.

    If all parameters are valid, the VdpCmR shall then add a new Data Point Sample Information (DPSI) with the vdpslotid from the API call in the VDP_SLOT_ID of the DPSI to the data message buffer.

    When this is successful, the VdpCmR shall return E_OK. ⌋

    Adding too big sample Upstream requirements: ⌈ The VdpCmR shall return E_NOT_OK if a data message is passed by VdpCmR_AddSample that is bigger than VdpCmRMaxDataLen. ⌋

    Argument invalidity to VdpCmR_AddSample is mostly explained in .

    Get current timestamp Upstream requirements: , ⌈ When VdpCmR_AddSample is called, VdpCmR shall retrieve the current timestamp by StbM_GetCurrentTime and time base identifier VdpCmRStbMSynchronizedTimeBaseRef. ⌋

    27. 错误处理¶

    原文标题：Error handling

    Most potential errors reported to the DCA Remote are sufficiently specified in . In particular a non-successful call to VdpCmR_AddSample may be answered by VDPCMR_E_BUFFER_FULL, which shall also be used when the module internal data message buffer is full and needs to be transmitted before the call to VdpCmR_AddSample can be successful.

    AddSample Buffer full Upstream requirements: , , ⌈ The VdpCmR shall always reserve space in the data message buffer to append an asynchronous error ASYNC_ERR which indicates that the data message buffer is full, i.e. (EC) = 0x74. If the remaining buffer space is not sufficient to store the next DPSI for the data sample provided with VdpCmR_AddSample, the VdpCmR shall append the previously mentioned asynchronous error to the data message buffer and request sending it in the next call to VdpCmR_MainFunction.

    The VdpCmR_AddSample shall then return VDPCMR_E_BUFFER_FULL. ⌋

    Maximum timestamp length Upstream requirements: , ⌈ The VdpCmR shall limit the size of DDLE encoded timestamps to configuration parameter VdpCmRMaxRelTimestampLen.

    28. Submission of Asynchronous 错误¶

    原文标题：Submission of Asynchronous Errors

    When a DCA Remote calls VdpCmR_AddAsyncError, the VdpCmR adds an asynchronous error to the data message buffer. These errors are transmitted within the data frame as a specific type of the data point information. In general, this function is similar to VdpCmR_AddSample except that instead of a data point error information is contained.

    Adding asynchronous errors Upstream requirements: , ⌈ The VdpCmR shall be able to receive asynchronous error information with the service VdpCmR_AddAsyncError.

    If all parameters are valid, the VdpCmR shall add a new Asynchronous Error Information (ASYNC_ERR) with the VDP_SLOT_ID set to the vdpslotid from the API call to the data message buffer.

    When this is successful, the VdpCmR shall return E_OK ⌋

    Argument invalidity to VdpCmR_AddAsyncError is mostly explained in .

    Error Information Upstream requirements: ⌈ When VdpCmR_AddAsyncError is called, the error information length ERR_LEN in the ASYNC_ERR shall be set to the value of errorInfoLen and errorInfoLen bytes shall be read from ptrErrorInfo and inserted into the ERR_INFO field of ASYNC_ERR. ⌋

    29. 错误处理¶

    原文标题：Error handling

    Most potential errors reported to the DCA Remote are sufficiently specified in .     Cyclic transmission Upstream requirements: ⌈ In case the transmission mode cyclic is set, the VdpCmR shall validate on call of VdpCmR_MainFunction, whether the cycle time is expired. If so, VdpCmR shall request sending the data message in this call of VdpCmR_MainFunction. ⌋

    31. 持久化 of Dynamic Configurations¶

    原文标题：Persistency of Dynamic Configurations

    VdpCmR might persist the Dynamic Configuration of data points to be able to start immediately with data collection after start-up, e.g. after a reset. It will not persist collected data.

    Persistency Upstream requirements: ⌈ The VdpCmR shall be able to conditionally persist the DP_DCFG in the NvM. ⌋

    NvM Block Descriptor Upstream requirements: ⌈ The NvM block descriptor referenced by ECUC parameter VdpCmRNvmBlockDescriptor, shall be a block processed during NvM_ReadBlock, NvM_WriteBlock, NvM_GetErrorStatus or NvM_SetRamBlockStatus. ⌋

    NvM Block Name Upstream requirements: ⌈ The supported NvM block name shall be VdpCmR_NvmRomBlockData. ⌋

    Read Persistent Data Upstream requirements: ⌈ The VdpCmR shall use the function NvM_ReadBlock to read the persistent VdpCmR data block from the NvM. ⌋

    Write Persistent Data Upstream requirements: ⌈ The VdpCmR shall use the function NvM_WriteBlock to write the persistent VdpCmR data block to the NvM. ⌋

    Get Persistent Data Error Status Upstream requirements: ⌈ The VdpCmR shall use the function NvM_GetErrorStatus to get the NvM block dependent status and error information. ⌋
